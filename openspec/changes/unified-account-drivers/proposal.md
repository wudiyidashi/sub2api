# 一套面板与可选账号管理驱动

状态：已实施首个可用 preset，完整目标仍按阶段推进。研究与实施日期：2026-10-09。

## 用户目标

在 Sub2API 的同一套面板完成账号添加、授权、导入、编辑、额度查询和运行管理；可按账号选择原生或增强管理方式。继续使用 Sub2API 的用户、API Key、订阅、支付、分组、代理、调度和计费功能，并降低持续跟进 Sub2API 与 codex-proxy-rs 新改动的成本。

## 推荐方案

以 Sub2API 为唯一主系统，引入账号驱动注册表。原有服务通过薄适配器成为原生驱动；Codex 增强能力以受管 Rust 驱动交付，界面、账号持久化、调度与计费由宿主统一承担。Rust 驱动只处理明确交给它的账号操作与一次上游执行，不运行第二套账号池、控制台、用户体系或费用账本。

新增账号时分别选择平台、管理方式和接入方式。旧账号缺少驱动绑定时继续使用原生路径。增强驱动只对实际支持并已验收的平台、认证类型和协议开放，首批聚焦 OpenAI/Codex。

驱动开发扩展现有 PluginManager、包校验、配置与运行状态设施；现有 HTTP transport v1 插件继续可用。完整账号驱动使用独立协商的新增能力，不能把当前 transport v1 的 HTTP 转发能力当作已经具备 OAuth 管理与原生 WebSocket 支持。

## 实现前必须证明

1. CPR 相关 Rust 模块能通过薄适配层完成指定账号的一次请求，不启动其 Store、Admin、Core 调度或后台刷新任务。
2. Go 宿主与 Rust 驱动的握手、双向流、取消和进程关闭在目标平台上可行；普通 gRPC 服务不自动兼容现有 go-plugin 握手与 broker。
3. 驱动结果可以接入现有 usage、限流、账号状态和计费入口，错误不引起不安全重试。

概念验证失败时，原生驱动和统一面板仍可独立交付；增强驱动不以内部网关桥接冒充实现，也不提前展示可用。

## 为什么选择这条路径

| 路径 | 单面板与原有功能 | 后续更新成本 | 判断 |
| --- | --- | --- | --- |
| 两套完整网关，隐藏 CPR 面板 | 可以包装，但仍有双账号状态、双调度和双重试 | 集成简单，运行与一致性成本较高 | 不作为推荐架构 |
| 把 CPR 全部翻译成 Go | 容易统一主系统 | 每次 Rust 改动需再次移植和验收 | 不适合持续快速跟进 |
| 重建主系统，只复用部分 Sub2API 页面 | 需要重新接入大量既有业务 | 初期开发与回归范围最大 | 无必要 |
| Sub2API 主系统 + 可替换驱动 | 一套业务模型与面板，按账号选择能力 | 宿主小范围适配，Rust 内部按版本跟进 | 推荐，先验证可抽离性 |

不能承诺任意上游功能无修改直接合并。Sub2API 更新主要通过维护分支合并；CPR 更新主要进入独立 Rust 驱动，涉及宿主合同的新功能仍需修改适配层并验收。

## 交付边界

当前已交付业务代码、持久化绑定、同一面板的两种方式、受管 Rust HTTP/SSE 与 WS 模块、固定源锁/补丁、可选统一镜像与运行验证。模块授权、导入、刷新和额度沿用原生服务；WS opening 复用 CPR，连接池和逐轮业务处理沿用 Sub2API。账号维护切换、运行时热升级、旧代次排空和上一代回滚已接入；独立 CPR 生命周期和跨宿主 owner 路由仍未开放。没有部署或修改既有服务，已有桥接草稿保留。
